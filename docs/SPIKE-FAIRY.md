# Spike: Fairy-Stockfish for escalating board sizes

> **Status (2026-10-09): carried out.** This spike's recommendation was implemented. The game runs on Fairy-Stockfish + ffish (`src/chess/`, `src/engine/`), and board sizes shipped as the *Growing board* mode (5×5 → 8×8). See DESIGN.md "Board Sizes" and SIMULATION.md §9–10. The throwaway spike code (`spike/`) was deleted; this write-up is kept for its measurements, especially the 10×10 numbers for any future boards past 8×8.

**Question:** can the game run battles on boards other than 8×8 (start around 5×5, grow to 8×8 or larger) in the browser?
**Answer: yes.** Fairy-Stockfish (WASM) plus the ffish rules library handle 5×5 through 10×10 with our rules. They're fast, stable in 200 games, smaller to download than today's engine, and work on GitHub Pages through a service-worker workaround.

Originally on branch `fairy-stockfish-spike` (2026-10-09, since deleted). Throwaway code lived in `spike/`.

## What was tested

- **Engine:** `fairy-stockfish-nnue.wasm` 1.1.12 (GPLv3), which reports itself as `Fairy-Stockfish … LB`. LB is the largeboard build: boards up to 12×10.
- **Rules:** `ffish` / `ffish-es6` 0.7.10 (GPLv3) for legal moves, check, mate, draws and FEN on any board size. This would replace chess.js, which is 8×8-only.
- **Variants:** `spike/variants.ini` (now generated by `variantsIni()` in `src/chess/boardSpec.ts`) defines `acc5`, `acc6`, `acc7`, `acc8` and `acc10`. All use standard pieces, no castling, a pawn two-step from each side's second rank and promotion on the last rank.
- **Armies:** random armies scaled to the board, placed in home rows with our king/pawn rules. The first mover is random unless a king starts in check.
- **Play:** depth 8, MultiPV 3, random pick within 50 centipawns of the best move (as in the game), 90-ply limit.
- **Node benchmark:** `node spike/bench.cjs 30`, 30 games per size.
- **Browser page:** `npm run dev`, then open `/spike/`. 10 battles per size in Chromium, plus a run with no isolation headers to mimic GitHub Pages.

## Results

| Board | Home rows | Army pts | Checkmate | Draw | Move limit | Avg plies | ms/move (Node / browser) | Worst move (browser) |
|---|---|---|---|---|---|---|---|---|
| 5×5 | 2 | 6 | 50% | 47% | 3% | 35 | 4 / 6 | 94 ms |
| 6×6 | 2 | 12 | 57% | 30% | 13% | 52 | 9 / 9 | 106 ms |
| 7×7 | 2 | 20 | 60% | 13% | 27% | 67 | 30 / 15 | 145 ms |
| 8×8 | 3 | 30 | 43% | 13% | 43% | 72 | 23 / 26 | 150 ms |
| 10×10 | 3 | 45 | 33% | 0% | 67% | 80 | 36 / 39 | 214 ms |

The percentages are from the 30-game Node runs; the browser runs of 10 games matched. On a 16-core desktop:

- **Stability:** 0 hangs and 0 illegal engine moves in 150 Node games and 60 browser games. The current Stockfish hangs about once per 1000 battles.
- **Init:** engine plus ffish start in about 1.3 s.
- **Download:** about 800 KB gzipped (`stockfish.wasm` 492 KB, `ffish.wasm` 310 KB, plus small JS). Today's Stockfish lite is 1.19 MB gzipped. Fairy-Stockfish ships no NNUE network for custom variants and uses its classical evaluation, which is plenty at depth 8.
- **Speed:** even the worst moves fit inside the game's 400 ms-per-move animation at 1×. Phones were **not measured**. Expect 3–6× slower: averages still fine, but worst moves on 10×10 could reach about 1 s, so big boards may need depth 6–7 on slow devices.

**How the games look:**
- **Small boards are decisive and fast:** 5×5–7×7 end in mate 50–60% of the time, against 29–50% for today's 8×8 at 60–90 plies. That fits short, punchy early rounds.
- **5×5 draws a lot:** 47%, mostly bare kings or insufficient material with 6-point armies. Bigger early armies, or counting those as "on points", would fix it.
- **10×10 mostly hits the move limit:** the armies start 4 ranks apart. Bigger boards need a longer limit, or a limit that scales with board size.

## Gotchas found

1. **Multithreaded build needs cross-origin isolation.** The WASM build uses pthreads, so it needs `SharedArrayBuffer`. Browsers only allow that when the page is served with the COOP/COEP headers, and GitHub Pages can't send headers.
   - **Workaround (tested):** [`coi-serviceworker`](https://github.com/gzuidhof/coi-serviceworker) (MIT, one small script). It registers a service worker that adds the headers, reloading the page once on the first visit. With the dev server sending no headers, the page still became isolated and battles ran normally.
   - **Side effect:** every resource the page loads must be same-origin or CORS-enabled. That's fine today, since everything is self-hosted.
2. **Node 26 needs `delete globalThis.fetch`** before loading the engine. The old Emscripten loader otherwise tries to `fetch()` a file path. This only matters for the simulator.
3. **Black's pawn two-step rank must be set per board size** (`doubleStepRegionBlack`). The default is rank 7, which doesn't exist on small boards.
4. **The CommonJS `ffish` exports the module object itself**, ready on `onRuntimeInitialized`. The ES-module build (`ffish-es6`) is a normal async factory; use that one in the browser.

## Recommendation: go

The engine side is solved. The cost is the refactor around it:

| Area | Work | Size |
|---|---|---|
| Rules layer | Replace chess.js with ffish in `position.ts`, `battle.ts` (mate, draws, material) and `runBattle.ts`. Wrap it behind a small interface so tests can use it in Node. | M |
| Board size as data | A `BoardSpec { files, ranks, homeRows }` passed through placement, AI placement scoring, FEN building and the UI. The piece-composition limit becomes per-size. | M–L |
| Engine | Swap the worker for Fairy-Stockfish plus variants.ini, keeping the `Candidate`/`pickMove`/eval-bar code. Add coi-serviceworker. Keep the 10 s timeout as a guard. | S–M |
| UI | Placement board and battle view render any size; square size fits the screen. | M |
| Run design | Board schedule per round (e.g. 5×5 rounds 1–2, 6×6 3–4, 7×7 5–6, then 8×8+). Budget and army cap per size. Move limit per size. What happens to an army that doesn't fit when the board changes: it can't shrink, but it can grow. | design + M |
| Simulator | Same engine swap (Node), then rebalance every size. | M |
| Saves | Saved runs need the board size; old saves would have to be discarded or migrated. | S |

Overall: a large but well-understood change. Roughly 2–4 focused sessions plus a balancing pass, best done on a branch. Suggested order: (1) the rules layer behind an interface, keeping 8×8 working with Fairy-Stockfish, so the game plays identically to today; (2) make board size data-driven; (3) the board schedule and balance.

## Decisions needed before building

- **Board schedule:** which sizes in which rounds, and whether the run ever goes past 8×8.
- **Home rows per size:** e.g. 2 rows on 5×5–7×7 and 3 on 8×8+.
- **Budget per size:** whether points scale with squares, and whether a small board caps the army so later purchases wait for the bigger board.
- **Move limit:** a fixed 90 plies or scaled by board size.
